# Workflow: sigcomply-cli

This file binds the shared `task-workflow` skill (`.claude/skills/task-workflow/SKILL.md`) to the
CLI repo. Read it with [AGENTS.md](../../AGENTS.md) before step 1 of any task.

The CLI is a binary, not a service. There is no web UI, no deploy, no database and no error
tracker. Don't import those assumptions from the Rails dashboard repo.

## What a push to main triggers

- `test.yml` on every push: fixture scan, full suite with `-race` and the 80% coverage floor,
  golangci-lint, and a cross-platform build matrix. On a push that also releases, it runs twice
  (directly and through `auto-release.yml`). On a docs-only push it still runs, so
  `TestDocFiguresMatchCode` gates docs pushes.
- `security.yml` on every push, every pull request and weekly: dependency, code and secret
  scanners. Several steps are warn-only (`continue-on-error`, `|| echo ::warning::`), so a green
  run does not mean no findings. Read the logs when a change touches dependencies.
- `auto-release.yml`, unless every file changed in the push matches its `paths-ignore`: root
  `*.md`, `docs/**`, `.claude/**`, `.vale/**`, `.vale.ini`, `LICENSE`, `.gitignore`,
  `.github/workflows/docs-lint.yml`. It calls `test.yml` and waits for it, then:
  1. Reads the subjects (not bodies) of every commit since the last tag. `<type>!:`, or the
     words "breaking change" anywhere in a subject in any case, means major. So
     `fix: handle breaking changes in Okta API` is a major bump. A `feat` subject means minor,
     anything else means patch. Commits from earlier doc-only pushes count toward the next
     release, so a docs subject containing "breaking change" makes the next code release major.
  2. Tags, builds with GoReleaser, attests build provenance, and publishes a GitHub Release with
     notes generated by `gh release create --generate-notes`.
- `docs-lint.yml` runs Vale on the customer-facing Markdown the push changed (`README.md`,
  `SECURITY.md`, `CONTRIBUTING.md` and `docs/**/*.md` except `docs/claude/**` and
  `docs/architecture/**`; every customer doc when `.vale.ini`, `.vale/**` or the workflow itself
  changes) and fails on error-level alerts.
- The GitHub E2E repo resolves `releases/latest` on its daily cron, so a release reaches it on the
  next scheduled run. The GitLab E2E repo pins `SIGCOMPLY_VERSION` in its `.gitlab-ci.yml`, so it
  runs a new release only after someone bumps that pin by hand.

Doc paths that are not path-ignored, so a push that changes only them still cuts a (patch)
release:

- Markdown outside the repo root and `docs/`: `internal/sources/sourcetest/README.md`,
  `contracts/README.md` and any other nested `*.md` (`*.md` matches root files only).
- `llms.txt`, `examples/**`, `cmd/sigcomply/templates/**`.
- `.github/pull_request_template.md`, `.github/ISSUE_TEMPLATE/*`, `.github/dependabot.yml`.

Batch edits to these with a code change, or accept the patch release.

The commit type sets the release. Pick `feat` only for a user-visible capability.

To push without releasing, put the skip marker (`[skip release]`, or a `chore(release)` subject)
in the head commit's message deliberately, and only then. The job matches it anywhere in the head
commit's full message, so never quote it in a body by accident. A release that was skipped or
path-ignored can be cut by hand with `workflow_dispatch` on `auto-release.yml`. `release.yml` is a
separate manual release that takes an explicit version.

After pushing, watch the runs: `gh run list --branch main`, then `gh run watch <id>`. A red
`main` is fixed before anything else.

## Gate: run before every commit

```
make test && make lint
```

Add, when the change calls for it:

| Change | Also run |
|---|---|
| `sigcomply build`, `plugin/`, or anything the heavy tests cover | `make test-full` |
| Source plugin, cassette, or `contracts/` | `make test-contract` and `make check-fixtures` |
| Coverage-sensitive change (new package, large deletion of tests) | `make test-coverage` and compare the total with 80% (CI enforces it, make does not) |
| `.github/workflows/*` | `actionlint` (install it yourself; it is not in `mise.toml`) |
| `go.mod` / `go.sum` | `go mod tidy` and commit the result |
| Customer-facing Markdown | `vale --minAlertLevel=error <files>` (Vale is pinned in `mise.toml`) |

Lefthook (`lefthook.yml`, installed by `make hooks-install`) is a backstop, not the gate. Run the
gate yourself and read the output before you commit.

- pre-commit: gofmt on staged Go files, `go vet ./...`, `make lint` and `make test` (these four
  only when Go files are staged), a `go mod tidy` check (when `go.mod` or `go.sum` is staged), and
  `gitleaks protect --staged`.
- pre-push: `make lint`, `go test -short -race ./...`, `gitleaks detect`.
- Only CI runs: the full suite without `-short`, the 80% coverage floor, the cross-platform build
  matrix, the `security.yml` scanners, weekly `contract-drift.yml` and nightly `live-saas.yml`.

`make ci` (`deps lint test build`) and `make pre-commit` are local bundles. Neither reproduces CI:
both use `-short` tests and neither enforces coverage.

## Test layers

The canonical test architecture is
[11-testing-strategy.md](../architecture/11-testing-strategy.md) (layers L0 to L4b). Summary:

| Layer | Where | Run with |
|---|---|---|
| L0/L1 unit and integration | `*_test.go` next to the code | `make test`, `make test-full` |
| L2 cassette and conformance | `*_conformance_test.go`, `testdata/` cassettes; fixture-vs-spec for GitHub and Okta | `make test-contract` |
| L3 vendor spec drift | `contracts/`, `scripts/contracts-fetch.sh` | weekly `contract-drift.yml`; `make contracts-diff` |
| L4a live | `//go:build live` tests | nightly `live-saas.yml`; `make test-live` (needs creds) |
| L4b released-binary end-to-end | `../sigcomply-cli-testing-project-github`, `../sigcomply-cli-testing-project-gitlab` | their own CI: GitHub against `releases/latest`, GitLab against its pinned `SIGCOMPLY_VERSION` |

Which tests to add:

- Any logic change: L0/L1 unit tests first (fake API client, deterministic `Now` seam), then a
  happy-path integration test.
- New or changed source plugin: also an L2 conformance test with a scrubbed cassette and an L3
  `contracts/<provider>/<service>` snapshot, in the same change. The checklist is "Testing a
  source plugin (checklist)" in [04-source-plugins.md](../architecture/04-source-plugins.md);
  the harness is described in `internal/sources/sourcetest/README.md`.
- Cloud submission contract (`internal/core/cloud*`, `internal/aggregator/`): the counts-only
  reflection test (`TestSubmissionPayload_StructurallyCountsOnly`) and the golden wire contract
  (`TestCloudV3_GoldenWireContract`, fixture `internal/aggregator/testdata/cloud_v3_golden.json`)
  stay green. Regenerate with
  `go test ./internal/aggregator/ -run TestCloudV3_GoldenWireContract -update`, then copy the
  file to `../sigcomply/spec/fixtures/files/contract/` in the same task. The cross-repo byte
  comparison runs only when the Rails repo is checked out next to this one, so CI skips it.
- New command or flag: a test in `cmd/sigcomply/` that runs the command and checks output and
  exit code.
- Published counts: `TestDocFiguresMatchCode` (`internal/manualcatalog/doc_figures_test.go`)
  checks exact substrings in the docs it lists. It matches raw bytes, so a line wrap, `**` or a
  changed dash inside a pinned phrase breaks it. When it fails, update the doc it names.

## Verify in the real product

Verification means building the binary and running the affected command:

```
make build
./bin/sigcomply <command>
```

| Change touches | Run | Check |
|---|---|---|
| a source, policy or the evaluator | `sigcomply check` against a fixture or scratch project (or an E2E repo) | stdout run summary, exit code (0 pass, 1 violations, 2 execution error, 3 config error), vault artifacts under `{framework}/{period_id}/run_*/` |
| the manual-evidence catalog or SPA contract | `sigcomply evidence catalog -o json` | JSON matches `sigcomply-evidence-spa/src/types/catalog.ts` |
| manual evidence due-dates | `sigcomply evidence due` | lists the expected entries; exits 0 whatever it finds, 3 on a config error ([commands](../reference/commands.md#sigcomply-evidence-due)) |
| the auditor read path | `sigcomply report --view <view>` | the view renders from the vault |
| CI scaffolding | `sigcomply init-ci` in a scratch dir | workflow files written as expected |
| cloud payload | `sigcomply check --capture-cloud-payload <file>` | the file holds counts only |
| version or build wiring | `sigcomply version` | version, commit and build time |

The built-in `run` skill can drive this. No browser is involved here; any machine-specific setup
is in `AGENTS.local.md`.

For source-plugin or CI-integration changes that need real infrastructure, the L4b E2E repos run
the released binary:
[sigcomply-cli-testing-project-github](https://github.com/SigComply/sigcomply-cli-testing-project-github)
and
[sigcomply-cli-testing-project-gitlab](https://gitlab.com/sigcomply/sigcomply-cli-testing-project-gitlab)
(cloned at `../sigcomply-cli-testing-project-*`). They see a change only after it is released.

## Repo-specific review lenses

The self-review "contracts and invariants" lens checks every Sacred Invariant in AGENTS.md
against the diff, and also:

- Aggregation boundary: nothing new on `SubmissionPayload` can carry an identifier; the
  reflection test and golden contract still pass; Rails strong-params in `../sigcomply/` match.
- Evidence flows: no third flow and no evidence sub-types in the evaluator; `validatePDF` stays
  stdlib byte checks.
- Signing: per-file ephemeral keys, signatures over canonical JSON, the run manifest still
  covers every file the run writes.
- Evidence-type contracts: no source IDs in policies, no policy IDs in plugins, schemas
  satisfiable by every plausible source.
- Cadence: manual folders keyed by the entry's cadence; every run artifact keyed by the run's
  period.
- Manual catalog export: shape still matches `sigcomply-evidence-spa/src/types/catalog.ts` and
  stays config-independent.
- `init-ci` templates and `examples/`: no untrusted `${{ github.event.* }}` interpolated into
  `run:` steps (GitHub Actions injection), pinned action SHAs, least-privilege `permissions`.
- Public repo: no secrets, personal emails, SSH host aliases, local paths or private Rails
  details in committed files, cassettes or fixtures.
- Release impact: the commit type matches the change, and no commit message quotes the skip
  marker by accident.

## Pre-launch rules

- Maintainers commit and push straight to `main` after the gate and the review skills pass. No
  PRs for internal work. `CONTRIBUTING.md` and `.github/pull_request_template.md` govern
  external pull requests.
- No backward-compatibility code for local state. Cadence state files are recoverable by design
  (loss means the next run is a first run), so write no migrations, backfills or shims for them.
- Cross-repo contracts are the exception: the cloud payload, the catalog export and OIDC claims
  change in lockstep with `../sigcomply/` and `../sigcomply-evidence-spa/`, receiver first.
- Every push to `main` that touches a non-ignored path is a public release. Push only green,
  verified work.
- At public launch, internal work moves to pull requests with review, and this section changes.

## Debugging

1. Reproduce deterministically: a failing unit or contract test, or a replayed scrubbed cassette
   (`make test-contract`).
2. Read the run output. `sigcomply check` prints a fixed text summary; the exit code localizes
   the class (2 execution or policy `error`, 3 config). Vault artifacts under
   `{framework}/{period_id}/run_*/` show what was collected, evaluated and signed.
3. CI failures: `gh run list`, then `gh run view <id> --log-failed`. Reproduce with
   `make pre-commit` then `make test-full`, or `make test-coverage` for a coverage failure.
4. Real-infrastructure failures reproduce in the E2E repos against the released binary.
